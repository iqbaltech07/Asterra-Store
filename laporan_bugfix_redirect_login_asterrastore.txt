1. RINGKASAN MASALAH
--------------------------------------------------------------------------------
Ketika pengunjung yang belum login membuka halaman produk, misalnya:
https://asterrastore.biz.id/products/vip-ntflxshare30dgar14d-s2
kemudian menekan tombol "Beli Sekarang", modal autentikasi muncul:
- Judul: "Silakan Masuk ke Akun Anda"
- Tombol Utama: "Masuk Sekarang"
- Tombol Sekunder: "Daftar Akun Baru"

Tombol "Masuk Sekarang" berhasil mengarahkan pengguna ke halaman /login.
Namun, setelah autentikasi (Google OAuth) berhasil, pengguna selalu diarahkan
ke homepage (/) bukan kembali ke halaman detail produk yang sedang dibuka.

Perilaku yang diharapkan:
Setelah autentikasi berhasil, pengguna kembali ke URL asal:
/products/vip-ntflxshare30dgar14d-s2 (beserta query parameters jika ada).


2. AUDIT ALUR REDIRECT & AKAR MASALAH (ROOT CAUSE)
--------------------------------------------------------------------------------
Dari penelusuran kode aktual, ditemukan 4 penyebab utama:

a. Relative URL vs Absolute URL pada Social OAuth Better Auth:
   - Pada halaman /login, pemanggilan `signIn.social({ provider: 'google', callbackURL: callbackUrl })`
     meneruskan path relatif (misal: "/products/vip-ntflxshare30dgar14d-s2").
   - Di server Better Auth (oauth2/state.mjs dan api/routes/callback.mjs), handler
     redirect callback OAuth mengeksekusi:
     `toRedirectTo = (result.isRegister ? newUserURL || callbackURL : callbackURL).toString()`
   - Karena newUserCallbackURL tidak dikirimkan dan callbackURL bertipe path relatif,
     pada lingkungan tertentu / reverse proxy / cross-domain OAuth bounce, HTTP 302
     gagal menyelesaikan path relatif dan jatuh ke default baseURL (homepage /).

b. Tidak Adanya Persistence Cadangan Saat Third-Party OAuth Bounce:
   - Alur Google OAuth mengarahkan browser keluar dari domain AsterraStore menuju
     accounts.google.com lalu kembali ke server callback API.
   - Jika query string ?callbackUrl=... terpotong saat redirect kembali atau jika
     pengguna terlempar ke /login, state tujuan asal hilang sepenuhnya.

c. Pemeriksaan Parameter Query Terlalu Sempit di Halaman Login:
   - Halaman /login sebelumnya hanya membaca `searchParams.get('callbackUrl')`.
   - Variasi parameter standar lain seperti `callbackURL`, `returnUrl`, `returnURL`,
     `redirect`, atau `redirectTo` tidak diperiksa dan langsung diabaikan.

d. Logika Default Fallback pada Hook Pelanggan yang Sudah Login:
   - Di /login, inisialisasi `rawCallback = searchParams.get('callbackUrl') || '/'`
     menetapkan string '/' sebagai nilai raw target.
   - Akibatnya, `getSafeInternalRedirectUrl(rawCallback, '/profile')` membaca '/'
     sebagai target valid alih-alih fallback, sehingga pengguna terlempar ke '/'.

4. CARA REDIRECT DIPERTAHANKAN (DEFENSE-IN-DEPTH)
--------------------------------------------------------------------------------
Alur perlindungan dibuat dalam 4 lapisan:

1. Lapisan Parameter URL:
   URL produk di-encode dan diteruskan secara eksplisit via query string:
   /login?callbackUrl=%2Fproducts%2Fvip-ntflxshare30dgar14d-s2

2. Lapisan Storage (SessionStorage & Cookie Backup):
   URL target disimpan di client storage saat tombol modal ditekan dan saat /login
   dimuat. Jika query string terpotong akibat bounce pihak ketiga (Google OAuth),
   client langsung memulihkan halaman asal dari storage.

3. Lapisan Better Auth Server (Absolute Origin Binding):
   URL target diformat menjadi URL absolut resmi (misal:
   https://asterrastore.biz.id/products/vip-ntflxshare30dgar14d-s2) dan dipasok ke
   kedua opsi `callbackURL` dan `newUserCallbackURL`. Hal ini mencegah server Better Auth
   melakukan fallback ke root domain server.

4. Lapisan Sanitasi Anti Open Redirect:
   Fungsi `getSafeInternalRedirectUrl` menolak seluruh domain asing, protokol tidak aman,
   serta loop ke /login dan /register. Hanya path internal relatif atau domain resmi
   AsterraStore yang diizinkan.
